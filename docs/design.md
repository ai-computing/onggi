# Onggi design

Status: **draft v0.1** (2026-10-21) · [한국어](ko/design.md)

Onggi is a content-addressed store for model weights and accelerator-compiled artifacts on Kubernetes + llm-d.
It keeps one copy of every byte across vendors, versions and compile profiles, moves those bytes to the nodes that
need them before a pod asks, and hands them to any inference engine as plain files.

An *onggi* (옹기) is the Korean earthenware jar that stores and ferments food. Models go in; compiled artifacts come
out of the firing.

## 1. Problem

NPUs compile a model ahead of time. Each combination of model × compiler/SDK version × device × parallelism ×
sequence-length bucket × batch size × compile options is a separate artifact, and every SDK upgrade invalidates all
of them. On the lab's RNGD + ATOM node (measured 2026-10-21, details in [artifact-formats.md](artifact-formats.md)):

| | FuriosaAI RNGD | Rebellions ATOM |
|---|---|---|
| Graph files | `.edf`, KB to 16 MB, named by content hash; 531 files, 0.28 GB on the node | inside each `.rbln` |
| Weights | HF safetensors re-sharded, **byte-identical** to the source; one converted copy per artifact directory (3 copies of Llama-3.1-8B = 48 GB) | re-laid-out by the compiler and **embedded in every `.rbln`** |
| Footprint | small graphs, duplicated weights | 215 `.rbln` files, **979 GB**; one Llama-3.1-8B build set: 18 files, 246 GB |

Content-defined chunking over a 121 GB sample (HF source, RNGD params, six ATOM files) found:

- RNGD params vs HF source: 100 % shared.
- ATOM decode variants (batch 1/2/4, sequence 256/512): 99.3 % shared with each other.
- ATOM decode vs ATOM prefill: 27.5 % shared — the compiler uses two weight layouts.
- HF source vs ATOM: 0 % — the layout transform defeats cross-vendor dedup.
- Fixed-size blocks (1 MiB or 4 KiB) find 0 % between ATOM batch variants, because the same bytes sit at shifted
  offsets. Only content-defined boundaries find them.

The sample deduplicates 2.9×; applying the measured shares to the 246 GB build set gives an estimated 28–30 GB
(≈ 8×). The graphs are small; the waste is weight copies. The node's disk was 80 % full.

Beyond space, the same artifacts drive cold start (download, materialize, load), scale-from-zero latency and which
nodes a model can be placed on. Today these are handled by hand: a shared SMB volume, a discovery CronJob that
publishes an inventory ConfigMap every 10 minutes, and compile/move/remove Jobs generated by lmd-top.

## 2. Goals and non-goals

Goals

1. One stored copy of every distinct byte (weights, graphs, metadata) across vendors, SDK versions and profiles.
2. Artifacts present on the right node before the pod needs them; cold start measured and reduced.
3. Any engine (vLLM, vllm-rbln, furiosa-llm, rngd-pd, Optimus Prime) reads plain files — no engine changes.
4. Kubernetes-native: declared with CRDs, delivered with standard volume mechanisms, observable with Prometheus.
5. Multi-node from the start: storage and caches span nodes and survive node loss.
6. Integrate with the ai-rm stack through rm-core contracts (see [integration.md](integration.md)).

Non-goals (for now)

- Building a durable distributed object store. The durable tier is an existing one (§6).
- Changing vendor formats or compilers. Onggi stores what the vendor tools produce.
- KV-cache storage. The chunk layer could hold prefix KV blocks later; it is out of scope until P5.

## 3. Quality attributes

Targets are initial and are fixed by measurement in P0–P2 (ISO/IEC 25010 categories; trade-offs recorded as ADRs).

| Attribute | Target | How it is checked |
|---|---|---|
| Integrity | every byte handed to an engine is hash-verified; a corrupt chunk is never served | property tests, fault injection |
| Reliability | node loss or agent crash never loses a committed artifact; reads fall back to peers, then the durable tier | chaos tests, deterministic simulation |
| Storage efficiency | ≥ 5× on the ATOM build set above; RNGD param copies → 1 | `onggi dedup-report`, measured |
| Cold start | materialization ≤ local-disk read time when the node is warm; ≤ baseline OCI pull when cold | rm-bench `artifact-coldstart` vs baselines |
| Scalability | throughput grows with nodes (P2P); adding/removing a node moves ≈ 1/N of cached chunks | simulation, cluster runs |
| Operability | every state visible as a CRD and metric; every action reviewable before it runs | lmd-top, Grafana |
| Compatibility | OCI distribution and ModelPack-compatible manifests; vendor formats untouched | interop tests |

## 4. Design principles

| Principle | Source | Applied as |
|---|---|---|
| Decide quality attributes first; record trade-offs | ISO/IEC 25010, SEI ATAM, ADRs (Nygard) | §3 targets, `docs/adr/` |
| Hide what is likely to change behind a module boundary | Parnas (1972); Ousterhout, *A Philosophy of Software Design* | vendor formats live only in adapters; the core knows chunks and manifests |
| Ports and adapters; bounded contexts | Hexagonal architecture (Cockburn); DDD | four contexts: Catalog, Data, Placement, Build (§5) |
| Immutable, content-addressed data | git, OCI, restic | no cache invalidation; replicas cannot diverge |
| Verify at the end point | End-to-end argument (Saltzer, Reed, Clark 1984) | hash checked when bytes reach the node, not trusted from the path |
| Crash-only, level-triggered | Candea & Fox (2003); Kubernetes controllers | every operation idempotent; recovery = restart + reconcile |
| Stability patterns | *Release It!* (Nygard) | timeouts, retries with jitter, circuit breakers, bulkheads, backpressure |
| Placement without a central index | Dynamo (2007); rendezvous/HRW hashing (1998); CRUSH | owners computed from the chunk hash and membership |
| Content-defined chunking | LBFS (2001); FastCDC (2016) | dedup across shifted offsets (§1) |
| Test the distributed protocol, not just functions | FoundationDB simulation; Jepsen; chaos engineering | §11 |
| Build only what differentiates | — | durable storage, consensus and formats are reused (§6, ADR-0002) |

## 5. Domain model

Four bounded contexts, each with its own vocabulary and owner component:

| Context | Owns | Key terms |
|---|---|---|
| **Catalog** | what exists and what it is | `ModelSource`, `WeightLayout`, `Artifact`, `Manifest`, `Ref` |
| **Data** | bytes | `Chunk` (content hash), `Pack`, durable tier, cache tier |
| **Placement** | where bytes are and should be | `NodeArtifactCache`, owners, prefetch, eviction |
| **Build** | producing artifacts | `CompileRequest`, `Profile`, compile farm, adapters |

- A **ModelSource** is a set of source weights (HF safetensors) identified by the hash of its files.
- A **WeightLayout** names how a vendor arranges weights: `hf`, `rngd`, `atom-decode`, `atom-prefill`, …
  Weights in the same layout deduplicate; across layouts they do not (§1).
- An **Artifact** is one compiled build. Its **profile key** is
  `(model source digest, device, compiler+SDK version, layout, parallelism, sequence buckets, batch, options)`.
- A **Manifest** lists an artifact's files as ordered chunk lists plus metadata (toolchain, options, source). The
  manifest is itself a content-addressed object; its digest is the artifact's identity.
- A **Ref** is a mutable name → manifest digest (`llama-3.1-8b@atom/decode-s512-b4`). Refs are the only mutable
  state and the GC roots.

## 6. Architecture

```
 Users ── lmd-top (TUI) · onggi CLI · GitOps YAML
                │ Kubernetes API only
 ┌──────────────▼─────────────── Control plane ───────────────────────────────┐
 │ CRDs: ModelSource · ArtifactSet · CompileRequest · Ref · StorePolicy ·        │
 │       NodeArtifactCache                                                      │
 │ onggi-controller (controller-runtime, level-triggered)                        │
 │   compile farm · prefetch planner · GC · compaction · webhook (node affinity) │
 └──────────────┬───────────────────────────────────────────────────────────────┘
                │ refs in etcd (small); manifests and chunks in the data plane
 ┌──────────────▼─────────────── Data plane ──────────────────────────────────┐
 │ Durable tier: existing object store (MinIO distributed / Ceph RGW,            │
 │               erasure-coded, multi-node) — chunks, packs, manifests           │
 │ Cache tier:   onggi-agent on every node (DaemonSet, local NVMe)               │
 │               HRW owners per chunk · peer-to-peer fetch · hot-chunk replicas   │
 │ Hot:          files materialized on the node, loaded by the engine            │
 └──────────────┬───────────────────────────────────────────────────────────────┘
                │ CSI NodePublishVolume → bind mount (pod Pending until ready)
            engine pods (vLLM · vllm-rbln · furiosa-llm · rngd-pd · Optimus Prime)
```

Components

| Component | Language | Role |
|---|---|---|
| `onggi-controller` | Go | reconciles CRDs; schedules compile Jobs, prefetch, GC, compaction; mutating webhook |
| `onggi-agent` | Go | node cache, chunk server for peers, CSI node plugin, materializer, metrics |
| `onggi` CLI | Go | push, pull, inspect, `dedup-report`, ref operations |
| adapters | Python | read and write vendor artifacts (Furiosa, Rebellions, HF); run inside compile Jobs |
| `pkg/chunker` | Go | FastCDC + hashing; the single hot loop, benchmarked in CI |

Go for everything that runs in the cluster (controller-runtime, CSI, the llm-d Go template); Python only where the
vendor SDKs are (ADR-0006).

## 7. Key flows

**Publish** (compile Job or `onggi push`)

1. The adapter splits the artifact into weight files and graph/metadata files and tags each weight file with its
   layout.
2. Chunk every file (content-defined). Ask the durable tier which chunk hashes it already has.
3. Upload only missing chunks (packed into larger objects to keep object counts low).
4. Write the manifest (content-addressed).
5. Update the `Ref` with a compare-and-swap on its `resourceVersion`. **This is the only commit point.** A crash
   before it leaves unreferenced chunks for GC; a crash after it has published a complete artifact.

**Read** (a pod mounts `onggi` volume `ref: …`)

1. kubelet calls the agent's CSI `NodePublishVolume`; the pod stays Pending until it returns.
2. The agent resolves the ref, reads the manifest, and for each missing chunk asks, in order: local cache → owner
   nodes (HRW) and announced holders → durable tier.
3. Every chunk is hash-verified on arrival. Files are assembled on local disk (reflink/hardlink from the cache), then
   bind-mounted read-only. Engines need regular files; lazy FUSE reads are an option for cold start only (ADR-0004).

**Prefetch** — the controller turns placement decisions (rm-controller), scale-up signals (llm-d autoscaling, KEDA)
and `StorePolicy` pins into per-node prefetch work for the agents.

**GC** — mark-and-sweep from roots (refs, pins, in-use leases from mounted volumes) with a grace period; sweeping
runs in the durable tier and in each cache. No reference counting on the hot path (ADR-0005).

**Compaction** — *storage* compaction repacks chunks and drops superseded SDK versions; *semantic* compaction
proposes folding rarely used profiles into larger ones, from request-length statistics, with the padding cost shown
(lmd-top asks before it runs).

## 8. Multi-node storage

The durable tier and the cache tier have different jobs, which keeps each simple:

| | Durable tier | Cache tier |
|---|---|---|
| Holds | every committed chunk, pack and manifest | chunks recently used or prefetched on this node |
| Durability | erasure-coded across nodes by the object store | none: a lost cache is refilled |
| Placement | the object store's | HRW: owners = top-R nodes by `hash(chunk, node)` among live agents, spread over topology labels |
| Consistency | immutable objects; only existence matters | immutable; a chunk is valid if its hash matches |

- **Membership**: each agent holds a `Lease`; the live set changes owners for ≈ 1/N of chunks when a node joins or
  leaves (HRW property).
- **Hot chunks**: chunks referenced by many pods (one prefill layout for every replica) get more cache replicas, and
  peers fan out to each other so the durable tier is read once per wave.
- **Anti-entropy**: agents periodically compare per-node Merkle summaries of what they should hold and repair.
- **Backpressure**: per-node and per-link concurrency limits; serving reads have priority over prefetch (bulkheads).

Failure handling

| Failure | Behaviour |
|---|---|
| agent crash mid-download | partial chunks discarded (hash mismatch); restart resumes from the manifest |
| node loss | its cache is gone; owners recomputed; readers fall back to other holders or the durable tier |
| durable-tier node loss | covered by the object store's erasure coding |
| corrupt chunk anywhere | rejected by hash; fetched from another source; counted in a metric |
| controller down | existing mounts and reads continue; no new publishes or GC until it returns |
| network partition | reads continue from local and reachable peers; GC never deletes during an unknown lease state |

## 9. Kubernetes and llm-d attachment

Only extension points are used; neither Kubernetes nor llm-d is forked or patched.

- **CRDs** for every state, so lmd-top, the CLI and GitOps (Argo CD, Flux) all act the same way.
- **CSI** volume `onggi.ai-computing.io` (ephemeral inline) as the delivery path; Kubernetes image volumes and an
  init container are fallbacks (ADR-0004).
- **Scheduling** through a mutating webhook that adds preferred node affinity to pods with an onggi volume (prefer
  nodes that hold the artifact), in the spirit of the scheduler's ImageLocality plugin.
- **llm-d**: deployment manifests reference onggi volumes; llm-d autoscaling and KEDA scale-up signals trigger
  pre-warming; LoRA adapters from npu-train are served for dynamic loading next to the router's adapter affinity;
  llm-d-benchmark and inference-sim drive cold-start tests. See [integration.md](integration.md).
- **Metrics** `onggi_*` (and `airm_artifact_*` names from rm-core) for Prometheus, Grafana and lmd-top.

## 10. Interfaces (sketch)

```yaml
apiVersion: onggi.ai-computing.io/v1alpha1
kind: ArtifactSet
metadata: {name: llama-3.1-8b-atom}
spec:
  source: {modelSource: llama-3.1-8b-instruct}
  device: rebellions-atom
  toolchain: {optimum-rbln: "0.10.3"}
  profiles:
    - {role: decode, sequence: [512, 2048], batch: [1, 8]}
    - {role: prefill, sequence: [512, 2048], chunk: 512}
  placement: {pin: {nodeSelector: {rebellions.ai/atom: "true"}, replicas: 1}}
status:
  artifacts:
    - {ref: llama-3.1-8b@atom/decode-s512-b8, digest: "sha256:…", logicalBytes: 15.2e9, newBytes: 0.19e9}
```

```yaml
volumes:
  - name: model
    csi:
      driver: onggi.ai-computing.io
      readOnly: true
      volumeAttributes: {ref: llama-3.1-8b@atom/decode-s512-b8}
```

CLI: `onggi push <dir> --ref …`, `onggi pull <ref> <dir>`, `onggi inspect <ref>`, `onggi dedup-report <dir>…`,
`onggi ref set|get|rm`.

rm-core contract (proposed for protocol v0.2): `ArtifactStore` with `resolve(ref) → manifest`, `materialize(ref,
path)`, `publish(dir, ref, layout)`, registered under the `airm.artifact_stores` entry-point group.

## 11. Performance and verification strategy

- **Baselines from day 0**: plain OCI image pull, Nydus, Dragonfly, OME's model agent, rsync. Metrics: cold start
  (request → engine can load), p50/p99 materialization time, bytes stored, recovery time after node loss.
- **Benchmarks in CI** for the chunker, packer and materializer; a regression fails the PR.
- **Property-based tests**: chunk → reassemble is byte-identical for random inputs and random shifts.
- **Deterministic simulation** of placement, GC and ref updates with a virtual clock, network and failures.
- **Fault injection** on the lab cluster: kill agents mid-transfer, drop links, fill disks, delete durable chunks.
- **Fuzzing** of manifest and vendor-format parsers.
- **Chunk size** is chosen from measurements (ADR-0001): 64 KiB average found the shifted duplicates; weight-heavy
  data may favour 1–4 MiB for a smaller index.

## 12. Security

Content addressing makes tampering detectable; manifests are signed (cosign) for provenance. RBAC separates read,
publish, compile and delete. The CSI mount is read-only. No credentials or site addresses live in tracked files.

## 13. Roadmap

| Phase | Deliverable | Done when |
|---|---|---|
| P0 | `onggi dedup-report`; import of an existing store layout (`hub/`, `compiled/`) | §1 numbers reproduced from a command |
| P1 | chunker, durable-tier backend, CLI push/pull | the 246 GB ATOM set stored in ≈ 30 GB; pulled files byte-identical |
| P2 | agent + CSI volume + materializer | an engine serves from an onggi volume; cold start measured vs baselines |
| P3 | CRDs, controller, compile farm, GC | an `ArtifactSet` produces its artifacts unattended |
| P4 | prefetch, webhook placement, llm-d autoscaling hook | scale-from-zero cold start reduced and measured |
| P5 | semantic compaction; expert-granular MoE fetch; KV-block store study | trade-off measured on real traces |

## 14. Open questions

1. Does the ATOM toolchain have a supported way to share weights across profiles (one vendor build showed prefill
   15 GB + decoders 1 GB), which would beat dedup?
2. Chunk size and pack size for weight-heavy data (ADR-0001).
3. Durable tier for the lab: MinIO distributed vs Ceph RGW vs the existing SMB share behind a gateway.
4. How much of OME's model CRDs and agent can be reused instead of rebuilt.
