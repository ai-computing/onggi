# 컴파일 결과물 형식: 무엇이 들어 있고 얼마나 겹치는가

연구실 RNGD + ATOM 노드에서 2026-10-21 측정(읽기 전용) · [English](../artifact-formats.md)

## FuriosaAI RNGD (furiosa-llm 2026.x)

| 항목 | 확인 내용 |
|---|---|
| 그래프 | `.edf` 파일, 하나당 수 KB~16 MB, 내용 해시(sha256 또는 24자리 접두)로 이름 지정. 노드 목록을 담은 바이너리 |
| 가중치 참조 | `.w` 파일(약 2.5 KB zip, `data.pkl`)은 가중치를 가리킬 뿐 텐서 데이터는 없음 |
| 가중치 | `param_files/params-<모델>-<층>-W16A16KV16-shard_size=…-<해시>.safetensors/`: HF 체크포인트를 4개 파일로 다시 나눈 것. 바이트가 HF 원본과 **동일**(네 위치 64바이트 탐침 모두 발견, 내용 기반 분할 100% 공유) |
| 결과물 묶음 | `artifact.json`(컴파일러·furiosa-llm 버전, 텐서·파이프라인 병렬 크기, 파이프라인 메타데이터) + `binary_bundle.zip`(`.edf` 약 90개, 15 MB) + 토크나이저·설정 파일. 가중치를 뺀 Llama-3.1-8B 결과물: 34–53 MB |
| 노드 사용량 | `.edf` 531개, 합계 0.28 GB. 같은 Llama-3.1-8B 변환 가중치가 캐시 1곳과 결과물 디렉터리 2곳에 3벌(48 GB) |

그래프는 이미 작고 내용 주소 방식입니다. 낭비는 원본 체크포인트와 같은 변환 가중치의 복사본입니다.

## Rebellions ATOM (optimum-rbln / rebel-compiler)

| 항목 | 확인 내용 |
|---|---|
| 형식 | 컴파일된 그래프마다 `.rbln` 바이너리 하나, 헤더 `RBLN2024`; 옆에 `rbln_config.json` |
| 가중치 | 각 `.rbln`에 컴파일러 고유 배열로 **통째로 포함**(HF 원본과 공유 청크 0%) |
| 크기(Llama-3.1-8B) | decode·prefill 그래프 하나당 13.4–14.5 GB, bf16 가중치 크기와 비슷 |
| 빌드 묶음 하나 | 18개(decode S256/S512 × B1/B2/B4/B8, lm_head 포함·미포함; prefill S256/S512, 여러 chunk 크기): **246 GB** |
| 노드 사용량 | `.rbln` 215개, **979 GB** |
| 벤더 방식 빌드 | 다른 빌드는 `prefill.rbln` 15 GB와 `decoder_batch_1/8.rbln` 각 약 1 GB로, 한 번의 컴파일 안에서는 가중치를 공유하는 것으로 보임 |

## 얼마나 겹치는가

121 GB 표본(HF Llama-3.1-8B 원본 4개, RNGD 변환본 4개, ATOM 파일 6개)에 내용 기반 분할 적용(8바이트 창 해시, 평균
64 KiB, 최소 16 KiB, 최대 256 KiB; 청크마다 BLAKE2b-128).

| 비교 | 첫 파일 바이트 중 둘째 파일에도 있는 비율 |
|---|---:|
| HF 원본 ↔ RNGD 변환본 | 100% |
| ATOM decode B1 ↔ B2 | 99.3% |
| ATOM decode B1 ↔ B4 | 99.3% |
| ATOM decode S256 ↔ S512 | 99.3% |
| ATOM decode lm_head 포함 ↔ 미포함 | 92.4% |
| ATOM decode ↔ ATOM prefill | 27.5% |
| HF 원본 ↔ ATOM decode | 0% |

| 묶음 | 논리 크기 | 중복 제거 후 |
|---|---:|---:|
| HF 원본 | 16.1 GB | 16.1 GB |
| RNGD 변환본 | 16.1 GB | 0.1 GB |
| ATOM(6개) | 89.0 GB | 25.7 GB |
| **합계** | **121.2 GB** | **41.9 GB (2.9배)** |

ATOM decode 변형 하나가 늘 때마다 0.05–0.19 GB만 추가되고, 첫 prefill은 10.1 GB를 추가합니다(두 번째 가중치 배열).
이를 18개 빌드 묶음에 적용하면 246 GB가 약 28–30 GB(약 8배)로 추정됩니다. 18개 전체를 돌린 값이 아니라 표본의 파일별
비율로 계산한 추정치입니다.

고정 크기 블록 해시는 ATOM의 공유를 전혀 찾지 못합니다. 1 MiB·4 KiB 블록 모두 배치 변형 사이와 decode–prefill 사이에서
0%였지만, 한 파일의 48바이트 탐침은 다른 파일에서 발견됐습니다. 같은 바이트가 블록 배수가 아닌 만큼 어긋난 위치에 있기
때문입니다. **내용 기반 분할이 필수입니다.**

압축 효과는 작습니다: `.rbln`의 가중치 구간 8 MB에 zlib 6단계를 적용하면 1.29배.

## 설계에 주는 의미

1. 핵심 단위는 가중치. **가중치 배열**(`hf`/`rngd`, `atom-decode`, `atom-prefill`)별로 한 벌만 저장하고 그래프는 따로 저장
2. 청크 경계는 내용 기반이어야 함(ADR-0001)
3. 컴파일러가 가중치 배열을 바꾸는 경우 벤더 간 중복 제거는 불가; 같은 벤더·같은 배열 안에서는 가능
4. RNGD 배열은 HF 원본과 같으므로 RNGD 경로는 원본 체크포인트를 바로 참조할 수 있음

## 방법

노드에서 읽기 전용 스크립트로 수행: 파일 목록과 크기, 매직 바이트·헤더, 48/64바이트 부분 문자열 탐색, Python·NumPy로
고정 블록·내용 기반 청크 해시. 수치를 재현할 수 있도록 `onggi dedup-report`(P0)에 포함합니다.
